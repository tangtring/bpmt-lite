# bpmt-lite v1.4.1 设计说明

## 1. 目标与范围

`v1.4.1` 是 `v1.4.0` 的小版本迭代，按以下固定顺序一次性收口：

1. `Nginx` 单入口
2. API 模块分层
3. 数据库操作模块（`DbHelper` API 化）
4. 文档发布同步
5. 修复 GitHub issue `#9`、`#10`

本版本确认不保留 `v1.4.0` 路径兼容包袱，API 路径以 `v1.4.1` 新基线为准。

## 2. 设计约束

- 技术栈不升级：Java 8、Maven 3、Tomcat 7、MariaDB。
- API 路径风格固定为：`/api/v1/<module>/*`。
- 未来 compose 内多个服务实例不得复用同一个容器监听端口。
- Web/API 缓存策略保持：`HIBERNATE_CACHE=true`，Hazelcast 继续双 member 组网。
- 文档变更必须同步：README、维护文档、API 参考文档、OpenAPI、验收清单。

## 3. 架构与端口（Nginx 单入口）

### 3.1 服务拓扑

- 新增 `nginx` 服务作为唯一外部入口。
- `web` 和 `api` 继续独立容器，`mariadb` 继续共享。

### 3.2 端口策略

- compose 内端口唯一化：
  - `web` 容器监听 `8080`
  - `api` 容器监听 `8081`（由当前 `8080` 调整）
  - `mariadb` 容器监听 `3306`
- `nginx` 对外暴露默认 `80`（如需要可扩展 `443`）。

### 3.3 路由策略

- `/`、`/ueditor/` 路由到 `web:8080`
- `/api/` 路由到 `api:8081`

### 3.4 对外访问基线

- 平台入口：`http://127.0.0.1/`
- API 文档：`http://127.0.0.1/api/docs/`
- OpenAPI：`http://127.0.0.1/api/openapi.json`

## 4. API 模块分层

### 4.1 代码分层目标

将 API 从“单模块实现”调整为“模块并行扩展”结构，便于后续新增能力时按模块独立演进。

### 4.2 建议目录

- `com.riversoft.api.common`：统一响应、错误模型、requestId、通用工具
- `com.riversoft.api.auth`：HMAC 认证与上下文构建
- `com.riversoft.api.modules.dynamic_tables`：动态表模块
- `com.riversoft.api.modules.database_operations`：数据库操作模块

### 4.3 路径基线

- 动态表模块：`/api/v1/dynamic-tables/*`
- 数据库操作模块：`/api/v1/database-operations/*`

## 5. 动态表模块接口重规划

`v1.4.1` 以模块化命名重新发布动态表接口：

- `GET /api/v1/dynamic-tables`
- `GET /api/v1/dynamic-tables/{tableName}`
- `POST /api/v1/dynamic-tables`
- `PUT /api/v1/dynamic-tables/{tableName}`
- `POST /api/v1/dynamic-tables/{tableName}/ddl:sync`
- `GET /api/v1/dynamic-tables/templates`
- `GET /api/v1/dynamic-tables/templates/{templateCode}`
- `POST /api/v1/dynamic-tables/templates/{templateCode}:create-table`

边界保持不变：

- 不开放动态表删除接口
- 不开放动态表业务数据 CRUD

## 6. 数据库操作模块设计（DbHelper API 化）

### 6.1 模块定位

新增 `database-operations` 模块，对外暴露受控 SQL 能力，内部复用现有 `DbHelper` 与 `JdbcService`，不绕过现有服务栈。

### 6.2 接口与方法映射

为了与 `DbHelper` 方法名保持一致，对外接口定义为：

- `POST /api/v1/database-operations/query`
  - 映射 `DbHelper.query(String sql, Object... args)`
- `POST /api/v1/database-operations/exec`
  - 映射 `DbHelper.exec(String sql, Object... args)`（首版优先支持 varargs 形式）
- `POST /api/v1/database-operations/save`
  - 映射 `DbHelper.save(String sql, Object... args)`，返回自增主键 `Long`
- `POST /api/v1/database-operations/find`
  - 映射 `DbHelper.find(String sql, Object... args)`，返回单行 `Map<String, Object>`

### 6.3 安全约束

- `query` 与 `find`：仅允许 `SELECT`。
- `save`：仅允许 `INSERT`。
- `exec`：仅允许受控 DML（`UPDATE`、`DELETE`），默认拒绝高危语句（如 `DROP`、`TRUNCATE`、`ALTER DATABASE`）。
- 所有接口都走 HMAC 认证，不新增并行认证方案。

### 6.4 配置开关

- `BPMT_API_DBOPS_EXECUTE_ENABLED`：控制 `exec`/`save` 是否可写，默认 `true`，可显式关闭。
- `BPMT_API_DBOPS_MAX_ROWS`：限制 `query` 最大返回行数，防止超大结果集。

### 6.5 响应规范

沿用统一结构：

- 成功：`success=true`，`data` 有效，`error=null`
- 失败：`success=false`，`error` 包含稳定 `code/message/details/requestId`

## 7. 文档发布与 GitHub 同步

`v1.4.1` 发布时必须同步以下文档：

- `docs/v1.4.1/api-reference.md`（面向人类）
- `docs/v1.4.1/openapi.json`（面向 AI/工具）
- `docs/v1.4.1/api-acceptance.md`（验收清单）
- README（入口、端口、路径、模块说明）
- `docs/maintenance.md`（构建、运行、验收、排障）

## 8. issue 收口要求（#9 + #10）

GitHub open issue `#9` 与 `#10` 作为本版本最终 gate，放在本次迭代最后执行并验收：

- `#9`：修复默认配置或初始化链路，确保快照能力可用
- `#10`：修复任务列表点击“查看/处理”时错误跳转到异常 `.view` 链接的问题，确保从 `CommonFlowAction/taskList.shtml` 打开任务可正常进入办理页面
- 回归验证不影响：
  - `nginx` 单入口路由
  - API HMAC 鉴权
  - 动态表模块
  - 数据库操作模块
- 修复后在 release 文档与验收清单中记录，并关闭 issue

## 9. 验收基线

发布前至少通过以下 gate：

1. `docker compose config`
2. Java 8 全仓编译与 API 单测通过
3. `nginx` 单入口健康检查通过：
   - `/`、`/ueditor/`、`/api/docs/`、`/api/openapi.json` 均返回 `200`
4. `database-operations` 四个接口：
   - `query/exec/save/find` 的正向与拒绝场景通过
5. `issue #9` 与 `issue #10` 用例通过并记录
6. 文档四件套（README、maintenance、api-reference、openapi）同步完成

## 10. 回滚策略

- 入口回滚：移除 `nginx` 服务，恢复 `web/api` 直连端口方式。
- API 回滚：以 tag 回退到 `v1.4.0` 镜像与文档快照。
- 文档回滚：恢复 `docs/v1.4.0/*` 为发布参考基线。
