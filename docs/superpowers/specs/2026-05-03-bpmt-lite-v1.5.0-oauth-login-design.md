# bpmt-lite v1.5.0 外部系统 OAuth 登录设计

## 1. 背景与目标

`bpmt-lite` 已完成 Docker 化、H5 保守修复、独立 `api` 容器和 `nginx` 单入口基线。`v1.5.0` 的目标是让 BPMT 作为企业组织架构与权限中心，向外部异构系统提供统一登录鉴权能力。

本版本采用标准 OAuth2 Authorization Code 模式，不实现 OIDC。外部系统可以部署在 BPMT compose 内，也可以独立部署。普通用户访问外部系统时，如果没有第三方系统自己的登录态，第三方系统跳转到 BPMT 登录页，复用 BPMT 用户名密码体系完成登录；登录成功并通过外部系统权限校验后，第三方系统获得 `userid` 和不透明 `access_token`，再建立自己的登录态。

## 2. 范围

### 2.1 本版本包含

- BPMT 作为 OAuth2 Authorization Code 服务端。
- OAuth 主流程在 `bpmt-web/platform` 内闭环。
- 新增 `CM_THIRDPART` 和 `CM_THIRDPART_*` 数据模型。
- 新增外部系统主数据管理入口。
- 外部系统权限映射到现有 BPMT 权限体系。
- OAuth 端点：
  - `GET /oauth/authorize`
  - `POST /oauth/token`
  - `GET /oauth/userinfo`
- BPMT 菜单支持通过 iframe 打开第三方 URL。
- README、维护文档、OAuth 参考文档和验收清单同步。

### 2.2 本版本不包含

- OIDC Provider。
- `id_token`、OIDC discovery、JWKS。
- `refresh_token`。
- 跨系统单点登出。
- 授权同意页 consent。
- `userid + thirdpartKey` 独立权限校验 API。
- 任何 `bpmt-api` 容器内改动。
- 独立 `bpmt-thirdpart-login-demo` 仓库实现。
- 自动处理第三方页面禁止 iframe 的降级逻辑。

## 3. 设计约束

- 保持 Java 8、Maven 3、Tomcat 7、MariaDB。
- 不升级技术栈，不引入新的 Web 前端框架。
- 数据持久化遵守 BPMT 现有 Hibernate 方式。
- 表名和字段名采用 BPMT 现有下划线多段式命名。
- 外部系统相关表统一使用 `CM_THIRDPART_*` 前缀；主表使用 `CM_THIRDPART`。
- 授权关系复用现有 `CmPri`、`CmPriGroupRelate`、权限组、角色和组织关系，不新增并行授权体系。
- v1.5.0 不改动 `bpmt-api`。
- `userid + thirdpartKey` 独立权限校验 API 暂不在 v1.5.0 实现，后续版本单独设计。

## 4. 总体架构

服务角色：

- `bpmt-web/platform`：承载 BPMT 登录页、`SessionManager`、OAuth authorize/token/userinfo、外部系统管理界面、菜单 iframe 打开能力。
- `bpmt-api`：v1.5.0 不涉及，不新增接口，不调整 HMAC 认证。
- 第三方 Web 应用：维护自己的登录态；无登录态时发起 OAuth 登录；拿到 `userid` 后进入业务页面。

主流程边界：

1. 第三方系统访问自己的受保护页面。
2. 第三方系统发现无登录态，跳转 BPMT `/oauth/authorize`。
3. BPMT 复用现有登录页完成用户名密码登录。
4. BPMT 校验用户是否具备目标外部系统权限。
5. BPMT 生成授权码并回调第三方系统。
6. 第三方系统用授权码换不透明 token 和 `userid`。
7. 第三方系统建立自己的登录态。

BPMT 菜单 iframe 只负责打开第三方 URL。第三方页面在 iframe 中发现无登录态时，仍由第三方系统自己发起完整 OAuth 登录流程。

## 5. 数据模型

### 5.1 `CM_THIRDPART`

外部系统主数据表，也是 OAuth client 主数据表。

建议字段：

- `THIRDPART_KEY`：外部系统业务唯一标识。
- `THIRDPART_NAME`：外部系统名称。
- `CLIENT_ID`：OAuth client id。
- `CLIENT_SECRET_HASH`：OAuth client secret 哈希。
- `REDIRECT_URIS`：允许的回调地址白名单，支持多行或分号分隔。
- `HOME_URL`：第三方系统默认入口 URL。
- `PRI_KEY`：映射到现有 `CmPri` 权限点。
- `ACTIVE_FLAG`：启停状态。
- `DESCRIPTION`：说明。
- `CREATE_TIME`：创建时间。
- `UPDATE_TIME`：更新时间。

约束：

- `THIRDPART_KEY` 唯一。
- `CLIENT_ID` 唯一。
- OAuth `CLIENT_SECRET` 只在生成时展示一次，入库只保存哈希。
- `REDIRECT_URIS` 必须保存前校验格式；OAuth 流程中必须严格匹配。

### 5.2 `CM_THIRDPART_AUTH_CODE`

OAuth 授权码记录表。授权码只保存哈希，明文 code 只返回给浏览器跳转。

建议字段：

- `CODE_HASH`
- `CLIENT_ID`
- `THIRDPART_KEY`
- `USER_ID`
- `REDIRECT_URI`
- `STATE`
- `EXPIRES_AT`
- `USED_AT`
- `CREATE_TIME`

约束：

- 授权码默认 5 分钟过期。
- 授权码一次性使用；成功换 token 后写入 `USED_AT`。
- 换 token 时必须校验 `CLIENT_ID` 和 `REDIRECT_URI` 与授权码绑定值一致。

### 5.3 `CM_THIRDPART_ACCESS_TOKEN`

不透明 access token 记录表。token 只保存哈希，明文 token 只返回给第三方系统。

建议字段：

- `TOKEN_HASH`
- `CLIENT_ID`
- `THIRDPART_KEY`
- `USER_ID`
- `EXPIRES_AT`
- `REVOKED_AT`
- `LAST_USED_AT`
- `CREATE_TIME`

约束：

- access token 默认 2 小时过期，可通过配置调整。
- v1.5.0 不实现 refresh token。
- DB 持久化是 token 状态的 source of truth；缓存只作为后续优化，不是本版本必需项。

## 6. 权限模型

外部系统采用“两层模型”：

- `CM_THIRDPART` 保存外部系统主数据、OAuth client 配置和入口 URL。
- `CM_THIRDPART.PRI_KEY` 映射到现有 BPMT 权限点。

授权关系继续复用现有权限组配置。管理员在现有权限体系中给角色、组织或权限组分配外部系统权限。OAuth `authorize` 和外部系统入口判断使用 `CM_THIRDPART.PRI_KEY`。

菜单可见性仍按现有菜单权限判断。第三方系统 OAuth 是否允许访问，按 `CM_THIRDPART.PRI_KEY` 判断。推荐菜单权限和外部系统权限配置为同一授权边界，避免用户能看到菜单但 OAuth 登录被拒绝。

## 7. OAuth 流程

### 7.1 授权端点

`GET /oauth/authorize`

请求参数：

- `response_type=code`
- `client_id`
- `redirect_uri`
- `state`

处理逻辑：

1. 校验 `response_type=code`。
2. 通过 `CLIENT_ID` 查询启用状态的 `CM_THIRDPART`。
3. 校验 `redirect_uri` 在 `REDIRECT_URIS` 白名单内。
4. 如果 BPMT 当前没有登录态，进入现有 `login.jsp`；登录成功后回到原始 authorize 请求。
5. 通过 `PRI_KEY` 校验当前用户是否具备外部系统权限。
6. 写入 `CM_THIRDPART_AUTH_CODE`。
7. 302 回跳 `redirect_uri?code=...&state=...`。

### 7.2 换 token 端点

`POST /oauth/token`

请求参数：

- `grant_type=authorization_code`
- `code`
- `redirect_uri`
- `client_id`
- `client_secret`

处理逻辑：

1. 校验 client 凭证。
2. 校验授权码存在、未过期、未使用。
3. 校验授权码绑定的 `CLIENT_ID` 和 `REDIRECT_URI`。
4. 标记授权码 `USED_AT`。
5. 写入 `CM_THIRDPART_ACCESS_TOKEN`。
6. 返回不透明 token 和 `userid`。

成功响应：

```json
{
  "access_token": "opaque-token",
  "token_type": "Bearer",
  "expires_in": 7200,
  "userid": "admin"
}
```

### 7.3 用户信息端点

`GET /oauth/userinfo`

认证方式：

- `Authorization: Bearer <access_token>`

返回内容：

- `userid`
- 用户显示名
- 默认组织基础信息
- 默认角色基础信息

该端点只返回最小必要用户信息，不返回敏感字段。

## 8. OAuth 错误处理

- `client_id` 不存在、`redirect_uri` 不可信时，不回跳第三方，只显示 BPMT OAuth 错误页。
- 用户无外部系统权限时，如果 `redirect_uri` 已验证可信，可以回跳 `error=access_denied&state=...`。
- BPMT OAuth 错误页使用中文说明，例如“你没有访问该外部系统的权限”。
- `/oauth/token` 和 `/oauth/userinfo` 使用 OAuth2 风格 JSON 错误，不使用 `success/data/error` 包装。
- 稳定错误包括：
  - `invalid_request`
  - `invalid_client`
  - `invalid_grant`
  - `invalid_token`
  - `unsupported_grant_type`
  - `access_denied`

## 9. 管理界面

外部系统管理入口放在现有后台管理体系中，按 BPMT 既有 `Action + Service + JSP + Hibernate` 模式实现。

功能：

- 列表。
- 新增。
- 编辑。
- 启停。
- 查看 client 配置。
- 生成 client secret。
- 配置 `REDIRECT_URIS`。
- 配置 `HOME_URL`。
- 选择或同步创建 `CmPri` 权限点。

不做：

- 普通用户授权同意页。
- 外部系统独立授权表。
- OAuth client 自助注册。

## 10. 菜单 iframe 能力

v1.5.0 扩展菜单配置，允许菜单项指向第三方 URL。点击后在 BPMT 主工作区 iframe 打开 `HOME_URL` 或菜单项配置的 URL。

边界：

- BPMT 不在菜单点击时主动替第三方做 OAuth 包装。
- 第三方页面如果没有自己的登录态，由第三方系统自行跳转 `/oauth/authorize`。
- 第三方应用需要允许被 BPMT 域 iframe 内嵌。
- 如果第三方页面设置 `X-Frame-Options` 或 CSP 禁止内嵌，本版本不自动降级到新窗口，只在文档中说明接入要求。

## 11. 配置

建议新增配置项：

- `BPMT_OAUTH_AUTH_CODE_TTL_SECONDS`：授权码有效期，默认 `300`。
- `BPMT_OAUTH_ACCESS_TOKEN_TTL_SECONDS`：access token 有效期，默认 `7200`。
- `BPMT_OAUTH_ISSUER_BASE_URL`：对外访问基准 URL，默认跟随 `nginx` 单入口。

正式部署必须重新生成外部系统 `CLIENT_SECRET`，不能使用示例 secret。

## 12. 测试要求

单测至少覆盖：

- `client_id` 校验。
- `client_secret` 校验。
- `redirect_uri` 白名单校验。
- 授权码生成、过期、一次性使用。
- 授权码绑定 `CLIENT_ID` 和 `REDIRECT_URI`。
- access token 生成、过期、userinfo 校验。
- 用户无权限。
- 用户停用。
- 外部系统停用。
- OAuth `CLIENT_SECRET` 只保存哈希。

集成验收至少覆盖：

1. `docker compose config` 通过。
2. Java 8 全仓编译通过。
3. `bpmt-web + bpmt-mariadb + bpmt-nginx` 启动通过。
4. 初始化库包含一条可用的示例外部系统配置。
5. 浏览器访问模拟第三方受保护 URL，跳 BPMT 登录，`admin/admin` 登录后回调拿 code。
6. 用 code 换 token，响应包含 `access_token` 和 `userid=admin`。
7. 用 token 调 `/oauth/userinfo` 返回 `admin` 基础信息。
8. 无权限用户访问同一第三方系统返回 `access_denied`。
9. BPMT 菜单点击第三方 URL 可在主页面 iframe 打开。
10. `/`、`/ueditor/` 回归仍为 `200`。
11. 现有 `/api/docs/`、`/api/openapi.json` 回归仍为 `200`，但 v1.5.0 不要求新增 API 内容。

## 14. 后续独立能力

### 14.1 `userid + thirdpartKey` 权限校验 API

该接口后续版本单独设计和实现，不纳入 v1.5.0。目标是校验 `userid` 这个 BPMT 用户是否具备 `thirdpartKey` 这个第三方系统的访问权限。

后续设计边界：

- 它不属于 OAuth 流程。
- 它不是 token introspection。
- 它不读取、不写入 `CM_THIRDPART_AUTH_CODE` 和 `CM_THIRDPART_ACCESS_TOKEN`。
- 它不校验 OAuth access token，也不依赖浏览器登录态。
- 它可以通过 `thirdpartKey` 解析第三方系统权限定义，默认从 `CM_THIRDPART` 读取 `PRI_KEY` 和启停状态。
- 它应作为独立 `bpmt-api` 权限校验接口设计，认证方式和 HMAC 凭证模型另行确认。

### 14.2 后续独立 demo 仓库

`bpmt-thirdpart-login-demo` 不在 v1.5.0 本仓实现。后续单独创建 GitHub 仓库，使用 Node.js 或 Python 等非 Java 技术栈，实现完整第三方登录流程：

1. 访问受保护页面。
2. 无登录态时跳 BPMT `/oauth/authorize`。
3. 回调拿 code。
4. 服务端换 token 和 `userid`。
5. 建立 demo 应用自己的 session。
6. 展示当前登录用户。

v1.5.0 的 BPMT 端协议和文档必须足够完整，使该 demo 仓库可以直接按文档接入。
