# bpmt-lite v1.6.0 HTTPS 支持设计

## 1. 背景与目标

`bpmt-lite` 已完成 Docker 化、H5 修复、独立 API 容器、`nginx` 单入口、OAuth 登录和 Web/API multi-arch 镜像发布。当前默认入口仍是 HTTP。由于原 BPMT 项目早期没有系统考虑 HTTPS，代码中存在两类问题：

- `nginx` 只在入口层启用 HTTPS 时，后端仍可能按 Tomcat 内部 HTTP 请求生成绝对 URL。
- 前端页面、JSP 和历史静态资源中存在实际运行会加载的 `http://` 外部资源，HTTPS 页面下会产生 mixed content 或加载失败。

v1.6.0 的目标是让 `bpmt-lite` 的 Web、UEditor、OAuth、H5 和 API 都能在 HTTPS 公开入口下正确运行，同时保留现有 HTTP 快速启动体验。

本版本的核心定位是“统一入口 HTTPS 化”，不是升级技术栈，也不是给 Tomcat 内部启 TLS。

## 2. 范围

### 2.1 本版本包含

- `bpmt-nginx` 支持内置 TLS 终止。
- `docker-compose.yml` 增加 HTTPS 端口、证书挂载和开关配置。
- 本地自签证书生成脚本，便于开发和发布验收。
- HTTPS 启用时，HTTP 默认 `301` 跳转到 HTTPS，并提供关闭开关。
- 后端统一识别可信 `X-Forwarded-*` 头，生成公开 HTTPS URL。
- Web 和 API 复用同一套公开 URL 推导规则。
- 实际运行所需的核心前端资源本地化或 HTTPS 化。
- README、维护文档、v1.6.0 验收文档和 AGENTS 交接信息同步。
- HTTPS 浏览器 smoke、API smoke、OAuth smoke 和 HTTP 回归验收。

### 2.2 本版本不包含

- Tomcat 内部 HTTPS。
- Web/API 容器直接暴露到公网。
- ACME/Let’s Encrypt 自动申请和续期。
- HSTS 默认强制开启。
- 全仓清理所有 `http://` 文本。
- 改造第三方库 demo、注释、XML namespace、协议标识中的 `http://`。
- 重构前端框架或替换 BPMT 旧页面体系。

## 3. 设计约束

- 保持 Java 8、Maven 3、Tomcat 7、MariaDB。
- 保持 `bpmt-nginx`、`bpmt-web`、`bpmt-api`、`bpmt-mariadb` 服务命名。
- Web/API 仍通过 compose 内部 HTTP 访问 Tomcat。
- Web/API 仍各自内嵌 Hazelcast member，不新增 Hazelcast Server。
- API HMAC canonical path 仍签公开 path，例如 `/api/v1/...`，不把 scheme、host、port 纳入签名。
- `v1.5.0` OAuth、`v1.5.1` issue #10、`v1.5.2` OAuth 登录态切换、`v1.5.3` 非 80 端口 Host 保留、`v1.5.4` multi-arch 发布能力必须继续回归。
- 默认 HTTP 快速启动不能被破坏；HTTPS 通过环境变量和证书流程启用。

## 4. 总体架构

服务边界：

- `bpmt-nginx`：唯一公开入口，负责 HTTP/HTTPS 监听、证书加载、HTTP 到 HTTPS 跳转、反向代理和可信代理头输出。
- `bpmt-web`：继续运行 `ROOT` 和 `/ueditor`，承载 BPMT Web UI、H5、OAuth、微信相关入口。
- `bpmt-api`：继续运行 `/api`，承载 API 文档和业务 API。
- `bpmt-mariadb`：不涉及 HTTPS 改造。

运行形态分两类：

1. 内置 TLS：
   - `bpmt-nginx` 暴露 HTTP 和 HTTPS。
   - 用户可以用脚本生成本地自签证书。
   - 生产环境可以把正式证书放入同一路径替换自签证书。
   - HTTPS 启用时，HTTP 默认 `301` 到 HTTPS。

2. 上游 TLS：
   - 外部负载均衡或网关先终止 HTTPS。
   - 上游把请求转发到 `bpmt-nginx` 或内部入口。
   - 后端通过可信 `X-Forwarded-*` 头识别公开 scheme、host、port。

本版本不在业务 Action 中逐个修补 URL，而是在 `Actions.Util.getContextPath()` 和 `Actions.Util.getFullURL()` 统一解决公开 URL 语义。

## 5. Compose 与 nginx 设计

### 5.1 Compose 配置

`docker-compose.yml` 保持默认 HTTP 可启动，并增加 HTTPS 配置项：

- `BPMT_HTTP_PORT`：HTTP 对外端口，默认 `80`。
- `BPMT_HTTPS_PORT`：HTTPS 对外端口，默认 `443`。
- `BPMT_HTTPS_ENABLED`：是否启用 HTTPS，默认 `false`。
- `BPMT_HTTP_REDIRECT`：HTTPS 启用时是否把 HTTP 跳转 HTTPS，默认 `true`。
- `BPMT_TLS_CERT_FILE`：容器内证书文件路径，默认 `/etc/nginx/certs/fullchain.pem`。
- `BPMT_TLS_KEY_FILE`：容器内私钥文件路径，默认 `/etc/nginx/certs/privkey.pem`。

证书目录约定：

```text
certs/fullchain.pem
certs/privkey.pem
```

`certs/` 作为运行目录，不提交真实证书和私钥。

### 5.2 nginx 配置生成

现有静态 `docker/nginx/nginx.conf` 不适合承载 HTTPS 开关、跳转开关和证书路径变量。v1.6.0 使用模板或启动前生成方式：

- 仓库保留 nginx 配置模板。
- `scripts/run.sh` 下载模板和生成脚本。
- 运行时根据环境变量生成实际 `docker/nginx/nginx.conf`。

nginx 生成结果需要覆盖三种场景：

1. HTTP-only：
   - 只监听 HTTP。
   - 保持 v1.5.4 默认启动体验。

2. HTTPS + redirect：
   - HTTP server 只做 `301` 到 HTTPS。
   - HTTPS server 代理 `/`、`/ueditor/`、`/api/`。

3. HTTPS + no redirect：
   - HTTP 和 HTTPS 都代理业务。
   - 用于少数兼容部署。

### 5.3 代理头

nginx 代理到 Web/API 时统一设置：

```text
Host: $http_host
X-Forwarded-Host: $http_host
X-Forwarded-Proto: $scheme 或明确的 https
X-Forwarded-Port: 公开访问端口
X-Forwarded-For: $proxy_add_x_forwarded_for
X-Real-IP: $remote_addr
```

HTTPS server 转发时必须让后端看到 `X-Forwarded-Proto=https`。非标准 HTTPS 端口必须通过 `X-Forwarded-Port` 或 `X-Forwarded-Host` 保留。

## 6. 证书脚本设计

新增脚本：

```text
scripts/generate-self-signed-cert.sh
```

职责：

- 生成 `certs/fullchain.pem` 和 `certs/privkey.pem`。
- 默认覆盖 SAN：`DNS:localhost`、`IP:127.0.0.1`。
- 允许通过环境变量追加域名和 IP。
- 已存在证书时默认不覆盖，除非显式传入覆盖开关。
- 输出证书位置和浏览器信任提示。

建议环境变量：

- `BPMT_TLS_HOSTS`：逗号分隔域名，例如 `localhost,bpmt.local`。
- `BPMT_TLS_IPS`：逗号分隔 IP，例如 `127.0.0.1,192.168.1.10`。
- `BPMT_TLS_DAYS`：证书有效天数，默认 `365`。
- `BPMT_TLS_FORCE`：是否覆盖已有证书。

`scripts/run.sh` 行为：

- `BPMT_HTTPS_ENABLED=1` 且证书不存在时，自动调用自签证书脚本。
- 下载或生成 nginx 配置后再执行 `docker compose up -d`。
- 启动完成后输出 HTTPS URL。

`scripts/install.sh` 行为：

- 保持现有一行安装入口。
- 支持：

```bash
BPMT_HTTPS_ENABLED=1 curl -fsSL https://github.com/wodenwang/bpmt-lite/raw/refs/tags/v1.6.0/scripts/install.sh | bash
```

生产证书不由 v1.6.0 自动申请。用户把正式证书放入 `certs/` 后重新启动即可。

## 7. 后端 URL 推导设计

### 7.1 统一入口

只在以下核心方法内实现公开 URL 推导：

- `Actions.Util.getContextPath(HttpServletRequest request)`
- `Actions.Util.getFullURL(HttpServletRequest request)`

影响范围包括：

- `_CP`
- `_FULL_URL`
- `RequestContext`
- `SessionContext`
- OAuth return URL
- 微信/企业微信认证回调 URL
- API 技术用户上下文
- 依赖 `Actions.Util` 的业务 Action

### 7.2 推导规则

`getContextPath()`：

1. scheme 优先取 `X-Forwarded-Proto` 的首个值。
2. host 优先取 `X-Forwarded-Host` 的首个值。
3. 若 `X-Forwarded-Host` 为空，取 `Host`。
4. 若 `Host` 也为空，回退到 `request.getServerName()` 和 `request.getServerPort()`。
5. port 优先取 host 内自带端口。
6. host 不含端口时，再取 `X-Forwarded-Port`。
7. `https:443` 和 `http:80` 省略端口；其他端口保留。
8. 拼接 `request.getContextPath()`。

`getFullURL()`：

1. 保留现有 `_full_url` 参数优先级，用于既有转发链兼容。
2. 未提供 `_full_url` 时，使用公开 base + `request.getRequestURI()` + query string 重建。
3. 不再直接使用 Tomcat 内部 `request.getRequestURL()` 作为最终公开 URL。

### 7.3 可信代理边界

后端会信任 `X-Forwarded-*` 头，因此部署边界必须明确：

- 默认 compose 只暴露 `bpmt-nginx`，不暴露 Web/API。
- Web/API 容器不得直接暴露到不可信网络。
- 若使用外部负载均衡，上游必须覆盖并规范设置 `X-Forwarded-*`，不能透传客户端伪造值。
- README 和维护文档必须说明该信任边界。

## 8. 前端资源治理

前端治理以实际运行风险为准，不做全仓文本清理。

### 8.1 核心资源本地化

`platform/src/main/webapp/h5/widget/h5_head.jsp` 中的核心运行依赖应本地化：

- jQuery。
- WeUI。
- jquery-weui。
- 其他 H5 主流程必须加载的 CSS/JS。

优先复用仓库已有静态文件。仓库缺失时，补入明确版本的本地静态资源，并记录来源和用途。

### 8.2 官方资源 HTTPS 化

必须使用官方外部地址的资源改为 HTTPS：

- `xhtml/frame/login.jsp` 中的微信登录脚本。
- `xhtml/frame_new/login.jsp` 中的微信登录脚本。
- `xhtml/frame/wx_binding.jsp` 中的微信绑定脚本。
- H5 中的微信 JS SDK，如果仍需外部加载，也必须改为 `https://res.wx.qq.com/...`。

### 8.3 非阻断项

以下不作为 v1.6.0 阻断范围：

- 第三方库 demo 页面。
- 注释中的链接。
- XML namespace。
- 许可证说明链接。
- 不在运行主路径输出的历史示例。

验收以浏览器实际加载、console、network failure 和 mixed content 为准。

## 9. API 与 OAuth 影响

### 9.1 API

API 文档入口保持：

- `/api/docs/`
- `/api/openapi.json`

业务 API HMAC 规则保持不变：

- canonical path 仍是公开 path。
- 不把 scheme、host、port 纳入签名。
- HTTPS 只影响 `BPMT_API_BASE_URL` 和浏览器/API 客户端访问地址。

`scripts/smoke-api.sh` 需要支持 HTTPS 自签证书场景，例如通过环境变量允许 `curl -k`。

### 9.2 OAuth

OAuth 端点保持：

- `GET /oauth/authorize`
- `POST /oauth/token`
- `GET /oauth/userinfo`

HTTPS 验收重点：

- 未登录访问 authorize，进入 HTTPS 登录页。
- 登录后回到原 HTTPS authorize 请求。
- 授权成功回调第三方时，不丢 scheme、host、非标准端口。
- 当前账号无权限时，OAuth 登录态切换页继续可用。
- 取消授权返回第三方时，错误回调保持 HTTPS 场景正确。

### 9.3 微信相关入口

现有微信/企业微信认证链路依赖 `Actions.Util.getFullURL(request)`。URL 推导修复后，HTTPS 场景下生成的认证回调地址应为公开 HTTPS 地址。

微信真实外部平台配置不作为本地自签证书 smoke 的必达项，但本地必须覆盖 URL 生成和页面资源加载。

## 10. 验收设计

### 10.1 静态检查

- `docker compose config` 通过。
- `scripts/verify-repo.sh` 通过。
- Java 8 全仓编译通过。
- API 单测通过。
- OAuth 相关目标测试通过。
- `rg` 检查实际页面中的高风险 `http://` 外链，排除第三方 demo、注释和 namespace。

### 10.2 HTTP 回归

`BPMT_HTTPS_ENABLED` 未启用时：

- `/` 返回 200。
- `/ueditor/` 返回 200。
- `/api/docs/` 返回 200。
- `/api/openapi.json` 返回 200。
- `scripts/smoke-api.sh` 通过。

### 10.3 HTTPS 自签证书 smoke

使用最小库启动临时 runtime：

```bash
BPMT_HTTPS_ENABLED=1 BPMT_HTTPS_PORT=18443 BPMT_HTTP_PORT=18080 docker compose up -d
```

期望：

- `https://127.0.0.1:18443/` 返回 200。
- `https://127.0.0.1:18443/ueditor/` 返回 200。
- `https://127.0.0.1:18443/api/docs/` 返回 200。
- `https://127.0.0.1:18443/api/openapi.json` 返回 200。
- `http://127.0.0.1:18080/` 返回 301，Location 指向 HTTPS。
- 最小库表数量仍为 176。
- Web/API Hazelcast 双 member 仍正常。

### 10.4 浏览器验收

使用 Playwright 或真实浏览器访问 HTTPS：

- 桌面登录页。
- H5 登录页：`/login.jsp?_action_mode=h5`。
- `admin/admin` 登录。
- 首页和菜单。
- H5 代表业务路径。
- 动态表代表路径。
- 工作流代表路径。
- `/oauth/authorize` 未登录和已登录路径。
- `/api/docs/` 静态文档页面。

验收标准：

- 页面可正常浏览。
- 无 mixed content 阻断。
- 无阻断性 console error。
- 无核心 CSS/JS 资源加载失败。
- 业务跳转生成 HTTPS URL。

### 10.5 API HTTPS smoke

使用：

```bash
BPMT_API_BASE_URL=https://127.0.0.1:18443/api scripts/smoke-api.sh
```

自签证书场景下脚本需要提供明确开关允许跳过证书校验。API 认证、签名和动态表列表 smoke 应通过。

### 10.6 继承回归

v1.6.0 发布前必须继承以下基线：

- v1.5.1 issue #10：完整库下工作流待办“查看/处理”不再生成 `_ORD_ID=null`。
- v1.5.2 OAuth 登录态切换。
- v1.5.3 非标准端口保留。
- v1.5.4 Web/API multi-arch manifest。

## 12. 实施顺序建议

1. 先做 nginx/compose/脚本，使本地能启动 HTTPS runtime。
2. 再做 `Actions.Util` URL 推导单元测试和实现。
3. 再治理实际运行前端资源。
4. 再补 API smoke、OAuth smoke 和浏览器 smoke。
5. 最后更新 README、维护文档、AGENTS 和 v1.6.0 验收记录。

这个顺序可以先建立可复现失败环境，再逐层消除 HTTPS 下的真实阻断点。

## 13. 风险与降级

- 自签证书会触发浏览器安全提示，这是开发体验预期，不作为缺陷。
- 如果某些微信外部脚本在本地自签 HTTPS 下无法完成真实平台认证，本地验收只要求页面加载和 URL 生成正确。
- 如果部分历史页面仍输出非主路径 HTTP 外链，先按浏览器 mixed-content 是否阻断分级处理。
- 若后端 URL 推导影响旧 HTTP 行为，必须优先修复统一工具方法，不能在业务 Action 中绕开。
- 若 HTTPS 启用导致 API 签名失败，优先检查 canonical path 是否意外引入 scheme/host。

## 14. 用户确认的决策

- 同时支持内置 nginx TLS 和外部上游 TLS。
- 证书采用本地自签生成 + 生产证书替换，不集成 ACME。
- HTTPS 启用时，HTTP 默认 `301` 跳转 HTTPS，并保留关闭开关。
- 后端公开 URL 推导信任 `X-Forwarded-*`，不新增 `BPMT_PUBLIC_BASE_URL`。
- 前端资源采用“核心运行资源本地化，官方外部资源 HTTPS 化”的策略。
- 推荐方案为 nginx TLS + 可信代理头 + 后端统一 URL 推导 + 前端资源治理。
