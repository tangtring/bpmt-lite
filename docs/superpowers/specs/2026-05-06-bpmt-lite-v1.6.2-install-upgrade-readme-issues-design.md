# bpmt-lite v1.6.2 安装升级与体验修复设计

## 版本定位

`v1.6.2` 是基于 `v1.6.1` 的补丁版本，定位为部署体验与第三方 OAuth 管理体验修复版。

本版本不升级 Java、Tomcat、MariaDB 或 nginx，不新增 API 协议，不扩展 OAuth 授权模型，不改变 `bpmt-api` 的公开接口范围。交付范围聚焦四件事：

- 修复 GitHub issue `#12`：第三方系统管理界面优化。
- 修复 GitHub issue `#13`：微信/企业微信 OAuth 登录权限不足提示增强。
- 重构 README，使其回到项目入口文档职责。
- 重构安装与升级脚本，形成一键安装和运行目录内升级路径。

## GitHub Issue 范围

### issue #12 第三方系统管理界面优化

现状：

- `platform/src/main/webapp/xhtml/thirdpart/ThirdpartAction/list.jsp` 列表字段过多，`homeUrl`、说明、微信登录等长内容让横向信息密度过高。
- `platform/src/main/webapp/xhtml/thirdpart/ThirdpartAction/form.jsp` 将基础信息、OAuth、微信登录、权限、状态和说明放在一个大表格中，维护者配置时不易扫描。

设计：

- 不引入新前端框架，不重构后台整体 UI。
- 列表页只保留核心列：系统名称/标识、Client ID、状态、微信登录、更新时间、操作。
- `homeUrl`、说明等长文本下沉到编辑表单或摘要展示，避免列表横向拥挤。
- 表单页按配置语义分块：
  - 基础信息。
  - OAuth 配置。
  - 微信登录。
  - 权限与状态。
  - 说明。
- `clientSecret` 重置字段增加明确提示：仅填写时重置，留空保持不变。
- 微信登录配置增加短提示：启用时必须选择企业号或服务号并填写对应 Key；只有服务号需要 Scope。

### issue #13 权限不足提示增强

现状：

- OAuth 权限不足已经有 `platform/src/main/webapp/xhtml/oauth/access_denied.jsp`，但页面和回调错误描述仍偏通用。
- 微信或企业微信登录完成后，如果当前 BPMT 用户没有目标第三方系统权限，用户需要看到更明确的原因。

设计：

- 保留现有 `access_denied.jsp`、切换账号、取消返回第三方系统机制。
- 页面主文案调整为明确句式：`用户[<userid>]不具备访问本应用权限。`
- 页面展示当前 BPMT 用户、目标第三方系统名称、系统标识或 clientId、Request ID。
- 页面保留两个操作：
  - 退出当前账号并重新登录。
  - 取消并返回第三方系统。
- OAuth 回调给第三方的 `error_description` 同步使用更清晰描述，但不泄露 `client_secret`、微信 code、access token、内部权限组明细等敏感信息。
- 本机 fake provider smoke 或对应测试覆盖权限不足文案。

## install.sh 设计

`scripts/install.sh` 是面向使用者的从零部署入口。README 只展示默认完整库安装路径：

```bash
curl -fsSL https://github.com/wodenwang/bpmt-lite/raw/refs/heads/main/scripts/install.sh | bash
```

行为：

- 默认创建 `bpmt-lite/` 运行目录。
- 默认初始化完整库 `bpmt`，下载并解压 `database/bpmt.sql.gz` 到 `db/init/bpmt.sql`。
- 安装后运行目录必须包含 `upgrade.sh`。
- 安装后运行目录继续包含 `docker-compose.yml`、nginx 模板、nginx 渲染脚本、证书脚本、数据库初始化脚本等必要文件。
- 默认执行 `docker compose up -d`。
- 保留 `BPMT_SKIP_UP=1` 作为只准备文件不启动的维护入口。
- 保留 `min` 入参能力，但不在 README Quick Start 中描述；只在脚本 `--help`、维护文档或验收文档中说明。
- HTTPS 仍沿用 `BPMT_HTTPS_ENABLED=1` 和既有 overlay 机制，README Quick Start 不展开复杂 HTTPS 流程。

## upgrade.sh 设计

`upgrade.sh` 是运行目录内升级入口。它管理运维状态文件，不向业务数据库写入升级记录。

默认行为：

- 默认跟随 GitHub Release/latest 或 tag 记录判断最新版本。
- 镜像升级采用 Docker 自身机制：
  - `docker pull ghcr.io/wodenwang/bpmt-lite:latest`
  - `docker pull ghcr.io/wodenwang/bpmt-lite-api:latest`
- 不自动修改用户已有 `docker-compose.yml`。
- 不自动升级或替换第三方容器镜像，例如 `mariadb`、`nginx`。
- 下载目标版本 compose 作为参考文件，例如 `docker-compose-v1.6.2.yml`，不参与默认启动。
- 版本间 SQL 升级脚本从目标 release/tag 对应源码下载并按版本顺序执行。
- SQL 执行记录写入运行目录文件，例如：
  - `.bpmt-lite/upgrade-state`
  - `.bpmt-lite/applied-upgrades.log`
  - `.bpmt-lite/last-version`
- 记录内容只包含运维态信息：已应用版本、SQL 文件名、执行时间、脚本校验值、目标 release/tag。
- 不在 MariaDB 中新建升级记录表，避免把运维状态混入业务数据库。

命令形式：

```bash
./upgrade.sh
./upgrade.sh v1.6.2
./upgrade.sh --dry-run
./upgrade.sh --from v1.6.1
```

约束：

- 如果 GitHub release/tag 查询失败，停止并提示原因，不猜测版本。
- 如果本地升级状态缺失，进入保守模式；除非用户显式传入 `--from <version>`，否则只打印需要人工确认的升级脚本列表。
- 如果数据库连接失败，停止，不执行 SQL。
- 如果 SQL 执行失败，停止，不继续重启 BPMT 服务。
- 已执行 SQL 再次运行时按本地记录跳过。
- 成功后只重建 BPMT 自有服务；不主动重建 `bpmt-mariadb`。

## 验收标准

基础验证：

- `scripts/verify-repo.sh`
- `docker compose config`
- Java 8 全仓编译：`mvn -s settings.local.xml -DskipTests compile`
- Web 镜像构建：`scripts/build-image.sh`
- API 镜像构建：`scripts/build-api-image.sh`

安装验证：

- 临时空目录执行公开默认 `install.sh`。
- 确认默认生成 `db/init/bpmt.sql`，不生成最小库作为主路径。
- 确认运行目录带出 `upgrade.sh`。
- 确认 `/`、`/ueditor/`、`/api/docs/`、`/api/openapi.json` 返回 200。

隐藏最小库能力验证：

- 维护验收中执行 `install.sh min`。
- 确认生成 `db/init/bpmt-min.sql` 并可启动 `bpmt_min`。
- README Quick Start 不出现 `min` 安装说明。

升级验证：

- `./upgrade.sh --dry-run` 能解析 latest release/tag，打印目标版本、参考 compose 文件名和待执行 SQL。
- 从 `v1.6.1` 临时运行目录升级到 `v1.6.2`。
- 确认只 pull BPMT 自有 latest 镜像。
- 确认不覆盖现有 `docker-compose.yml`。
- 确认下载 `docker-compose-v1.6.2.yml` 作为参考。
- 确认 SQL 升级执行成功并写入 `.bpmt-lite/` 本地记录。

issue 验收：

- issue `#12`：第三方系统列表更清晰，表单按语义分块，密钥重置提示存在。
- issue `#13`：OAuth 权限不足页面出现 `用户[xxx]不具备访问本应用权限`，并保留切换账号与取消返回能力。

README 验收：

- Quick Start 只保留默认完整库安装和升级主路径。
- Quick Start 不描述最小库。
- 所有相对文档链接存在。
- MIT 许可证与作者信息为 `wodenwang` 和 `borball`。

发布后验证：

- 推送 `v1.6.2` Web/API multi-arch 镜像。
- 同步 `latest`。
- 创建 Git tag 和 GitHub Release。
- 使用公开 release/tag 的 `install.sh` 完成一次全新安装验证。
- 在 GitHub issue `#12`、`#13` 评论验收结果并关闭。
